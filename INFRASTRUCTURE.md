## Astro version and Cloudflare adapter

- **Current stable Astro version (verified 2026-09-13):** `astro@7.3.2`, released 2026-09-08 per the official GitHub releases page. Astro 6 and 7 both shipped within the last year; 7.x is current stable. Source: [github.com/withastro/astro/releases](https://github.com/withastro/astro/releases).
- **Official Cloudflare adapter:** Yes — `@astrojs/cloudflare` is a first-party, Astro-maintained SSR adapter for deploying to Cloudflare Workers (with static assets), supporting `astro add cloudflare` for one-step setup, Workers KV-backed session storage, and Cloudflare image services integration. Sources: [docs.astro.build/en/guides/integrations-guide/cloudflare](https://docs.astro.build/en/guides/integrations-guide/cloudflare/), [docs.astro.build/en/guides/deploy/cloudflare](https://docs.astro.build/en/guides/deploy/cloudflare/), [npmjs.com/package/@astrojs/cloudflare](https://www.npmjs.com/package/@astrojs/cloudflare).

## Core Web Vitals current thresholds (verified 2026-09-13)

Per Google's web.dev guidance (fetched directly):
- **LCP (Largest Contentful Paint):** "good" ≤ **2.5 seconds**, measured at the 75th percentile of page loads, segmented by mobile/desktop. Source: [web.dev/articles/lcp](https://web.dev/articles/lcp).
- **INP (Interaction to Next Paint):** "good" ≤ **200 milliseconds**, "poor" > 500ms (per aggregated third-party summaries cross-referencing Google's published thresholds; INP replaced FID as a Core Web Vital in March 2024 and these thresholds have been stable since).
- **CLS (Cumulative Layout Shift):** "good" ≤ **0.1**, "poor" > 0.25.
- All three are evaluated at the 75th percentile of real-user (CrUX) field data, not lab data alone.

These are unchanged from the widely-cited 2024 thresholds; no revision was found as of this verification date. Recommend a final spot-check against `web.dev/articles/inp` and `web.dev/articles/cls` directly (not just LCP) immediately before launch, since Google does periodically revise these.

## Maximum traffic this free stack supports (plain English)

**The binding constraint is NOT what most people assume.** Because Cloudflare's static-assets requests are free and unlimited (confirmed directly from Cloudflare's static-assets billing docs, not just the general limits page), a mostly-static Astro site serving its HTML/CSS/JS/images as static assets does **not** burn through the 100,000-requests/day Workers limit just from people browsing the site. That 100k/day cap only applies to requests that actually invoke your Worker's JavaScript — in this architecture, that's essentially just:

1. The lead-form submission endpoint (writes to D1, sends via Resend, verifies Turnstile).
2. Any other dynamic API route you add (e.g., an interactive demo backend, if one exists beyond static demo pages).

**So the realistic ceilings, in order of what actually binds first:**

1. **D1 writes: 100,000 rows written/day.** Each lead submission is roughly 1 row write (maybe 2 if you log an audit row). That is **effectively unlimited for a lead-gen MSME site** — even a wildly successful campaign generating 1,000 leads in a single day would use 1% of this cap. This will not bind in realistic scenarios.
2. **D1 reads: 5,000,000 rows read/day.** Only relevant if you build an admin dashboard that queries leads frequently; for viewing a leads list a few times a day, this is not a realistic constraint.
3. **Workers invoking-requests: 100,000/day.** This only counts the form-submission endpoint and any other dynamic route. Realistically this means you could receive on the order of **tens of thousands of form submissions and dynamic API calls per day** before hitting it — again, far beyond what a marketing site with six demo pages will see. If, unusually, every static page load were misconfigured to route through the Worker (e.g., via `run_worker_first` matching too broad a pattern), this would become the binding constraint at 100,000 dynamic hits/day.
4. **Turnstile: unlimited challenges** per Cloudflare's own wording — will not bind.
5. **Resend: 3,000 emails/month, 100/day hard cap.** If every lead triggers 1 notification email to the studio + 1 optional autoresponder to the lead, that's 2 emails/submission, so the **effective daily ceiling is ~50 lead submissions/day (100 emails ÷ 2) before Resend's email cap becomes the binding constraint** — this is the most realistic "you will actually hit this" limit in the whole stack for a moderately successful lead-gen campaign. At 3,000/month ÷ 2 = ~1,500 lead-equivalent email pairs/month, which is a generous but not infinite ceiling.
6. **Cloudflare Pages (if used instead of/alongside Workers static assets): 500 builds/month** — relevant only to how often you redeploy, not to visitor traffic. At normal iteration pace (a few deploys/day during active development, then infrequent after launch) this will not bind.

**Translating to approximate monthly capacity:** For a typical MSME lead-gen marketing site with six demo pages, this stack can comfortably support **very high visitor volumes (plausibly hundreds of thousands of monthly page views, since static asset serving is unmetered)**, while the **realistic first ceiling to actually hit is Resend's email cap (~50 lead submissions/day / ~1,500/month)** if every lead sends two emails — not a bandwidth or server limit at all.

**What happens at each ceiling — pause vs. error vs. bill:**
- **Workers request limit exceeded:** further Worker-invoked requests **fail with an error** (not billed).
- **D1 read/write limit exceeded:** queries **fail with an error** (Cloudflare confirmed this is now actively enforced as of a Sept 1, 2026 change) — not billed, and existing data is not deleted.
- **D1 storage (5GB) exceeded:** you must delete data before inserting more or altering schema — again a hard stop, not an auto-bill.
- **KV limit exceeded:** operations of that type **fail with an error** — not billed.
- **Turnstile:** no cap to exceed on Free.
- **Resend limit exceeded (100/day or 3,000/month):** sends beyond the cap will fail/queue/bounce depending on Resend's exact enforcement (not fully confirmed from the fetched pricing page — verify directly in Resend's dashboard/docs at build time); this is the one place where the exact "what happens" mechanic should be double-checked before launch, since email delivery failure silently means **lost leads never reach the studio's inbox** even though the form technically "succeeded" from the visitor's point of view. Recommend building a D1 write as the source of truth regardless of email success, so no lead is ever lost even if Resend's cap is hit.

**Cheapest upgrade path if any ceiling is hit, with current prices (as verified 2026-09-13, subject to change):**
- **Resend** (most likely first ceiling): paid tier — verify current starting price directly in Resend's dashboard at time of upgrade; industry-standard low tiers for transactional-email providers in this class are commonly in the ~$20/month range, but this was **not directly confirmed from the fetched Resend pricing page** in this research pass and must be re-checked before quoting a number to a client.
- **Cloudflare Workers**: Workers Paid, **$5/month**, raises invoking-request allowances substantially and moves to usage-based billing beyond the included amount (confirmed structure, exact current included-amount figures should be re-verified against `developers.cloudflare.com/workers/platform/pricing` at upgrade time since Cloudflare has changed these numbers before).
- **Cloudflare D1**: bundled under the same Workers Paid plan; higher daily row read/write allowances apply once on a paid Workers plan.
- **Cloudflare Turnstile / Web Analytics**: no upgrade needed at any realistic MSME-site traffic level.

**Bottom line for the business plan:** the ₹0/month stack is not "small-site-only" — the static-asset-unlimited design of Cloudflare Workers means visitor traffic is not the binding constraint at all. The one line item that will realistically need a paid upgrade first, if the studio's lead-gen efforts succeed, is **email notifications through Resend**, and that upgrade is inexpensive relative to the value of not losing leads.

## Top risks flagged in this research (see also final summary to user)

1. **D1's daily limit enforcement is brand new (2026-09-01)** — behavior could still be in flux; re-verify close to build/launch.
2. **Netlify's free-tier numbers are ambiguous** between a legacy model and a newer credits-based model depending on account creation date — not a blocker since Netlify is only a fallback, but do not quote either figure to a client without checking the live account.
3. **Resend's exact overage/enforcement behavior** (queue vs. bounce vs. hard block) was not explicitly confirmed from the fetched pricing page and should be re-verified directly before launch, since this is the most likely real-world ceiling this project will hit.
4. **Vercel Hobby and Supabase Free are correctly disqualified** for this use case — Vercel Hobby's terms explicitly forbid commercial use, and Supabase Free's 7-day inactivity pause is a poor fit for an intermittent-traffic lead-capture backend. Neither should be substituted in without re-reading this reasoning.
